# 基于 Raspberry Pi 4B 的多模态智能轮椅控制系统——面试讲解文档

> 本文档依据当前仓库代码整理，重点解释“为什么选这些技术、数据怎样流动、代码怎样实现、面试官可能怎样追问”。没有在仓库中出现的训练指标、数据集规模、推理帧率和准确率均不虚构。

## 一、先统一项目事实

### 1. 推荐项目表述

**项目简介：** 面向无障碍出行场景，构建基于 Raspberry Pi 与 STM32 的边缘智能系统，实现语音、头部姿态等多源感知、端云通信及软硬件协同控制。

**技术栈：** Linux、Python、C、Raspberry Pi 4B、STM32F407、Vosk、PyAudio、pypinyin、OpenCV DNN、YOLO、ONNX、MQTT、OneNET、USART、ADC+DMA、DAC。

### 2. 仓库中的真实软硬件

- 树莓派端主要使用 Python，并不是 C++。
- MCU 工程的芯片头文件和链接脚本均指向 STM32F407，因此不应写 STM32F103。
- 树莓派端负责音频、图像和网络数据处理；STM32 负责实时串口接收、摇杆采样、控制仲裁和模拟量输出。
- 视觉模型为约 10 MB 的 ONNX 模型，实际输出形状为 `[1, 9, 336]`。
- ONNX 模型元数据中的类别顺序为：`front、right、up、left、down`。

## 二、面试开场怎么讲

### 1 分钟版本

这个项目采用 Raspberry Pi 4B 和 STM32F407 的异构架构。树莓派运行 Linux，承担计算量较大的离线语音识别、视觉推理和 MQTT 通信；STM32 负责 USART 指令接收、ADC+DMA 摇杆采样以及 DAC 控制量输出。

语音侧使用 PyAudio 获取 16 kHz 单声道 PCM 音频，通过 Vosk `KaldiRecognizer` 做流式离线识别，同时处理 Partial 和 Final 结果。为了降低中文近音误识别，我把指令词预转换为无声调拼音音节，并加入句尾约束、近音补偿、双级冷却和重复结果过滤。

视觉侧把训练后的 YOLO 模型导出为 ONNX，通过 OpenCV DNN 在树莓派 CPU 上推理。图像经过方形补边、归一化和 BGR 到 RGB 转换后送入网络，再完成输出转置、置信度筛选、坐标还原和 NMS，最终把识别类别映射为统一控制码。各输入源通过状态和锁进行互斥，控制码经消息队列和 USART 发送给 STM32；STM32 还设计了摇杆优先接管和超时停车机制，提高系统安全性。

### 面试官继续追问时的主线

始终围绕下面这条数据链展开：

```text
麦克风 ─→ PyAudio ─→ Vosk ─→ 拼音/规则后处理 ─┐
                                                ├─→ 状态仲裁 ─→ 消息队列 ─→ USART ─→ STM32

```

## 三、总体架构为什么这样设计

### 1. 为什么采用 Raspberry Pi + STM32

两类处理器的定位不同：

- Raspberry Pi 有 Linux、较完整的 Python 生态和更强的算力，适合运行 Vosk、OpenCV DNN、MQTT 等非实时任务。
- STM32 启动快、时序稳定、外设丰富，适合完成串口中断、ADC 连续采样和 DAC 输出等硬实时或准实时任务。
- 两者通过简单的单字节协议解耦。上层算法不直接操作轮椅模拟量，底层 MCU 也不需要理解语音、图像或 MQTT。

这种架构的核心不是“用了两块板”，而是把计算密集型任务和实时控制任务分开。

### 2. 树莓派端的并发结构

集成控制类启动了至少三个后台线程：

- 语音线程：持续读取音频并进行 Vosk 解码。
- 视觉线程：持续采集摄像头并进行 ONNX 推理。
- 活动监控线程：检查当前模式的最后活动时间，超时后发送停止码。

串口、传感器和 MQTT 还分别由独立线程运行。不同线程通过共享状态、互斥锁以及 `msg_queue.put/get` 接口协同。

使用线程的原因是这些任务包含大量阻塞 I/O：麦克风读取、摄像头读取、串口和网络等待。Python 的 GIL 对纯 Python CPU 密集任务有影响，但 Vosk 和 OpenCV 的核心计算在 C/C++ 扩展中完成，因此线程仍能用于组织并发 I/O 和底层推理调用。

### 3. 状态与互斥仲裁

程序维护两个关键状态：

- `SYSTEM_ACTIVE`：系统是否已经唤醒。
- `current_mode`：当前接受语音输入还是视觉输入。

两个状态分别由锁保护。普通控制指令必须同时满足“已唤醒”和“输入源与当前模式一致”才会进入消息队列。切换模式时先发送停止码，再修改模式，避免上一个输入源留下持续运动状态。

这里所谓“状态机”不是使用专门状态机框架，而是用状态变量、锁和条件分支实现的轻量状态控制逻辑。面试中应如实表述为“基于状态变量的控制状态机”。

## 四、OpenCV DNN、YOLO、ONNX 详细讲解

## 4.1 三个名词分别是什么

### YOLO

YOLO 是目标检测模型体系，负责从一张图像中同时预测目标位置和类别。在本项目中，类别不是常规的人、车等目标，而是 `front、right、up、left、down` 五种头部姿态。

模型一次前向推理会输出若干候选框，每个候选框包含：

```text
中心点 x、中心点 y、宽 w、高 h、5 个类别分数
```

### ONNX

ONNX 是模型交换格式，不是推理框架。训练后的模型被序列化成统一计算图，使模型能够脱离训练框架，在 OpenCV、ONNX Runtime 等不同推理引擎中加载。

选择 ONNX 的价值：

- 树莓派部署时不需要完整安装训练框架。
- 模型文件可移植，部署代码与训练代码解耦。
- OpenCV DNN 可以直接解析 ONNX 计算图。

### OpenCV DNN

OpenCV DNN 是 OpenCV 内置的深度学习推理模块，负责加载网络、设置输入并执行前向传播。项目使用：

```python
net = cv2.dnn.readNetFromONNX(onnx_path)
net.setPreferableBackend(cv2.dnn.DNN_BACKEND_OPENCV)
net.setPreferableTarget(cv2.dnn.DNN_TARGET_CPU)
```

即使用 OpenCV 后端在树莓派 CPU 上推理，没有使用 CUDA、TensorRT 或 NPU。因此面试中不能说做了 TensorRT 加速或硬件量化，除非后续确实补做。

## 4.2 摄像头采集

项目通过 V4L2 后端打开摄像头：

```python
cap = cv2.VideoCapture(CAMERA_ID, cv2.CAP_V4L2)
```

随后设置：

- MJPG 编码，减少 USB 摄像头传输压力。
- 采集宽度 128、高度 96。
- 目标帧率 10 FPS。
- 缓冲区长度为 1，尽量丢弃陈旧帧，优先处理最新画面。

代码还通过连续 `grab()` 后再 `retrieve()` 的方式刷新摄像头缓冲，并且每 20 个循环进行一次推理，目的是降低树莓派 CPU 占用。这里应说“采用跳帧推理控制负载”，不要宣称实际达到多少 FPS，因为仓库没有性能测试数据。

## 4.3 图像预处理

### 第一步：方形补边

摄像头图像可能是 4:3，而模型要求 128×128。程序创建一个边长等于原图长边的黑色方形画布，将原图放在左上角：

```python
h, w = image.shape[:2]
m = max(h, w)
square = np.zeros((m, m, 3), dtype=image.dtype)
square[0:h, 0:w] = image
```

这样做避免直接把长方形图像拉伸成正方形而改变头部比例。

严格来说，这段实现是“右侧或底部补黑边”，不是标准 YOLO 中居中并填充 114 灰色的 letterbox。因为项目最终主要使用类别而不是框的位置，影响相对有限；若要显示精确检测框，应记录缩放比例和 padding 偏移并进行反变换。

### 第二步：构造 Blob

```python
blob = cv2.dnn.blobFromImage(
    image,
    scalefactor=1.0 / 255.0,
    size=(128, 128),
    mean=(0, 0, 0),
    swapRB=True,
    crop=False,
)
```

`blobFromImage` 完成以下工作：

1. 将图像缩放到 128×128。
2. 将 `uint8` 像素从 0～255 归一化到 0～1。
3. 把 OpenCV 默认的 BGR 通道顺序转换为模型训练常用的 RGB。
4. 将数据布局从 HWC 转换为 NCHW。
5. 增加 batch 维度，最终输入通常为 `[1, 3, 128, 128]` 的 `float32` 张量。

为什么要保证预处理与训练一致？因为通道顺序、归一化方式、输入尺寸任何一项不一致，都会造成明显精度下降。

## 4.4 前向推理

```python
net.setInput(blob)
output_names = net.getUnconnectedOutLayersNames()
outputs = net.forward(output_names)
```

- `setInput` 将 blob 绑定到网络输入层。
- `getUnconnectedOutLayersNames` 获取没有后继节点的输出层名称。
- `forward` 按 ONNX 计算图执行卷积、特征融合和检测头计算。

本地模型的真实输出为：

```text
[1, 9, 336]
```

含义是：

- `1`：batch size。
- `9`：4 个框参数 + 5 个类别分数。
- `336`：候选预测数量。

这属于 YOLOv8/YOLO11 常见的无独立 objectness 输出形式，可以解释为 `[B, 4+C, N]`。后处理时要转置为 `[N, 4+C]`，即 `[336, 9]`，这样每一行代表一个候选框。

代码兼容 `[1, 9, 336]` 和 `[1, 336, 9]` 两种排列：当最后一维大于候选行数时执行转置。

## 4.5 置信度筛选与类别判定

对每个候选框，代码读取：

```python
box = row[0:4]
class_scores = row[4:9]
class_id = argmax(class_scores)
score = class_scores[class_id]
```

然后只保留分数高于 `0.45` 的候选框。

需要注意：当前集成代码对 `row[4:9]` 又执行了一次 sigmoid，但本地 ONNX 模型输出的类别字段已处于 0～1 范围。再次 sigmoid 会把分数压缩到约 0.5～0.73，使阈值失去原本意义。正确做法应先确认导出模型输出：

```python
class_scores = row[4:4 + len(CLASSES)]
# 如果导出图已经包含 sigmoid，直接使用，不再二次 sigmoid。
```

面试时可以这样回答：

> 我会先根据 ONNX 输出节点和数值范围确认检测头输出是 logits 还是概率。如果是 logits 才做 sigmoid；如果导出图已融合激活函数，则直接使用输出概率，避免重复激活导致阈值失真。

## 4.6 坐标还原

YOLO 输出的是中心点形式：

```text
(cx, cy, w, h)
```

OpenCV NMS 需要左上角形式，因此进行转换：

```text
left = cx - w / 2
top  = cy - h / 2
```

再乘以模型输入到补边图像的宽高比例，将坐标映射回图像尺度。完整表达为：

```python
left   = int((x - 0.5 * w) * x_factor)
top    = int((y - 0.5 * h) * y_factor)
width  = int(w * x_factor)
height = int(h * y_factor)
```

若后续需要可视化，还应把坐标裁剪到原始图像边界，并扣除标准 letterbox 的 padding 偏移。

## 4.7 NMS 为什么需要

YOLO 常会围绕同一个头部输出多个高度重叠的候选框。如果全部保留，同一帧会出现多个重复结果。

项目使用：

```python
cv2.dnn.NMSBoxes(
    bboxes=boxes,
    scores=scores,
    score_threshold=0.45,
    nms_threshold=0.50,
)
```

NMS 的处理过程：

1. 按置信度从高到低排序。
2. 保留最高分框。
3. 计算其他框与该框的 IoU。
4. 抑制 IoU 大于 0.5 的重复框。
5. 对剩余框继续执行相同步骤。

最后程序从 NMS 结果中选择置信度最高的检测作为当前姿态。

## 4.8 安全偏置与时序防抖

当预测结果为 left 或 right，但它与 front 的分数差小于 0.1 时，代码偏向选择 front。其思路是：转向比保持正向更容易造成误动作，因此边界样本优先选择风险更低的类别。

随后通过 0.4 秒防抖控制发送频率：

- 姿态发生变化时立即发送新控制码。
- 姿态不变时，只有超过防抖间隔才允许再次发送。

这相当于在模型输出之后增加时序滤波，避免单帧抖动和高频重复下发。

## 4.9 姿态结果如何进入控制链路

映射关系为：

| 视觉类别 | 控制码 |
|---|---:|
| front | F |
| down | B |
| left | L |
| right | R |
| up | S |

控制码不是直接写串口，而是先通过：

```python
msg_queue.put(MessageType.CONTROL_COMMAND, command)
```

交给串口线程统一发送，从而把视觉推理和硬件通信解耦。

## 4.10 当前视觉代码必须修正的类别顺序

本地 `best.onnx` 元数据记录的类别顺序是：

```python
["front", "right", "up", "left", "down"]
```

而最新版集成代码写成：

```python
["front", "left", "up", "right", "down"]
```

如果使用的是同一个模型，类别 1 和类别 3 会被解释反，造成左右颠倒。部署前必须以模型元数据或训练时的 `data.yaml` 为准统一顺序。

面试中可以把这当作模型部署经验来讲：

> ONNX 只输出类别索引，类别语义依赖训练时的 names 顺序。部署时我需要核对模型元数据，保证后处理端的类别数组与训练配置完全一致，否则网络推理正确也会被业务层错误解释。

## 4.11 为什么不用 Ultralytics 直接推理

仓库早期原型使用 `ultralytics.YOLO(...).predict()`。集成版本改为 OpenCV DNN，优点是：

- 部署依赖更轻，不需要完整 PyTorch/Ultralytics 运行环境。
- 能明确控制输入预处理、后处理和线程数。
- 更适合资源受限的树莓派 CPU 部署。

代价是需要自己实现输出解析、阈值筛选和 NMS，并且必须保证预处理、输出布局和类别顺序正确。

## 五、Vosk 流式离线 ASR 如何实现

## 5.1 音频采集

PyAudio 以以下格式打开麦克风：

```text
采样率：16000 Hz
采样格式：16 bit PCM
声道：单声道
缓冲块：1024 帧
```

每次从输入流读取 1024 帧并送入 `KaldiRecognizer.AcceptWaveform()`。16 kHz 与 Vosk 中文模型的期望采样率一致；单声道能够降低数据量和计算开销。

## 5.2 Partial 和 Final

Vosk 有两类结果：

- Partial：一句话尚未结束时的增量文本，例如“向”→“向左”→“向左转”。优点是延迟低，缺点是可能反复变化。
- Final：Vosk 判断一句话结束后的稳定文本。延迟略高，但更适合高风险近音补偿。

程序两者都处理：普通明确命令可从 Partial 快速响应；风险较高的别名只允许在 Final 且整句完全匹配时触发。

## 5.3 pypinyin 音节索引

Vosk 可能把相同或相近发音识别为不同汉字，例如：

```text
向左 → 向佐
前进 → 前景
左转 → 左传
```

程序启动时将所有控制词预先转换为无声调拼音音节：

```text
向左 → xiang zuo
向佐 → xiang zuo
```

运行时只转换当前 ASR 文本，再与预构建索引匹配。预计算减少了每个 Partial 结果反复转换固定词表的开销，`lru_cache` 也用于缓存重复文本的拼音结果。

## 5.4 句尾约束

如果只判断一句话中是否包含“停止”“左转”等词，普通聊天也可能触发控制。例如“我们刚才讨论了左转这个问题”。

程序设置以下规则：

- 整句话完全等于指令时允许触发。
- 指令位于去除语气词后的句尾时才继续判断。
- 两音节短指令出现在长句句尾时，前文还必须出现“请、给我、马上、我要”等控制提示词。
- 三音节以上、语义较明确的句尾指令可以使用稍宽松规则。
- “坐船”等高风险近音只允许 Final 整句完全匹配。

这不是深度语义模型，而是基于拼音序列位置和提示词的规则化意图约束。面试中不要称为“自然语言理解大模型”。

## 5.5 分级匹配评分

代码根据不同匹配方式赋予规则评分：

- 整句精确匹配：0.99。
- 无前缀的句尾匹配：0.97。
- 三音节以上句尾匹配：0.91。
- 带控制提示词的两音节句尾匹配：0.88。
- 高风险 Final 近音别名：0.90。

Partial 和 Final 还使用不同的最低阈值。

这里的“置信度”是业务层自定义的匹配评分，并非 Vosk 声学模型原生置信度。简历和面试中最好称为“分级匹配评分”或“规则置信度”，避免被追问时概念混淆。

## 5.6 双级冷却与重复结果过滤

Vosk 的 Partial 会不断累积，因此一次讲话可能产生多个相近结果。程序设计了三层过滤：

1. 最小处理间隔 0.12 秒，避免每个音频块都重复进行完整匹配。
2. 全局冷却 0.45 秒，任意命令触发后短时间内不再触发其他命令。
3. 同指令冷却 1 秒，同一命令短时间内不重复执行。

此外，程序把“识别文本拼音 + 命中命令 + 命中位置”组成指纹，保存到最大长度为 30 的 `deque`。同一指纹在 2 秒内再次出现时被视为重复 Partial 或回声结果并丢弃。

这就是“滑动窗口指纹去重”：窗口里只保存最近若干条记录，既能避免无限增长，又能识别短时间重复事件。

## 5.7 Recognizer Reset

程序在以下情况调用 `recognizer.Reset()`：

- 成功识别并处理一条命令后。
- 获得一句 Final 结果后。
- 连续 6 秒没有有效命令时。

目的是清空 Vosk 内部累积的语句上下文，防止上一句话残留在后续 Partial 中并再次命中。

## 5.8 “半双工回声抑制”到底是什么

程序播放“前进”“右转”等提示音后，扬声器声音可能重新进入麦克风，形成：

```text
识别命令 → 播放提示音 → 麦克风采到提示音 → 再次识别 → 重复执行
```

代码在播放后设置约 0.75 秒的忽略窗口：

```python
ignore_asr_until = time.time() + 0.75
```

窗口内仍然读取麦克风数据，但不继续处理识别结果。

这属于“应用层短时回声屏蔽”或“播报期间输入门控”，并不是真正的声学回声消除 AEC，也不是硬件半双工通信。面试中建议使用准确说法，避免面试官追问自适应滤波、参考信号和回声路径估计。

## 5.9 软件 Watchdog

独立线程每 0.5 秒检查当前模式的最后活动时间：

- 语音状态下，以最后一次检测到语音文本的时间为准。
- 视觉状态下，以最后一次检测到有效姿态的时间为准。
- 连续 60 秒无活动时，将 `SYSTEM_ACTIVE` 清零并发送停止码 `S`。

这属于应用层软件 Watchdog，不是 STM32 的 IWDG/WWDG 硬件看门狗。它防止上层长时间无输入时保持旧控制状态，但不能处理 Linux 完全死机或进程被强制终止。若要进一步提高安全性，应让 STM32 也实现通信心跳超时，并在超时后本地归零输出。

## 六、消息队列和统一控制码

不同输入源最终都转换成相同的单字节协议：

| 控制码 | 含义 |
|---|---|
| F | 正向控制 |
| B | 反向控制 |
| L | 左向控制 |
| R | 右向控制 |
| S | 停止 |
| A | 升档 |
| D | 降档 |

算法线程只生产控制消息，串口线程只负责发送：

```text
算法线程：识别结果 → msg_queue.put(CONTROL_COMMAND, code)
串口线程：msg_queue.get() → serial.write(code)
```

这种生产者—消费者结构降低了算法与硬件接口的耦合：更换视觉模型不会影响串口实现，更换串口设备也不需要修改 ASR 代码。

### 当前队列设计的隐患

当前串口线程和 OneNET 线程都从同一个 `msg_queue` 调用 `get()`，但各自只处理某一种消息类型。如果底层是普通竞争式队列，消息可能被错误消费者取走后丢弃。

更可靠的实现是：

- 使用 `control_queue` 和 `telemetry_queue` 两条独立队列；或
- 使用发布订阅 EventBus，为不同消息类型注册独立订阅者；或
- 单一 Dispatcher 线程消费总队列，再按类型路由到下游队列。

面试中可以把它作为“后续架构优化”回答，但不要声称当前已经实现可靠发布订阅。

## 七、MQTT 与 OneNET

树莓派使用 Paho MQTT 客户端连接 OneNET，核心流程为：

1. 创建 MQTT v3.1.1 客户端并配置设备认证。
2. 连接后订阅设备属性设置主题。
3. 在 `on_message` 回调中解析 JSON。
4. 将合法控制值写入控制消息队列。
5. 向属性上报主题发布设备状态和健康数据。
6. 对平台属性设置请求发送 `set_reply` 响应。

MQTT 适合该场景的原因是协议轻量、支持长连接与发布订阅、弱网下开销较小，并且 OneNET 原生支持物模型主题。

安全方面，设备密钥不应硬编码在源码中，应通过环境变量或受限配置文件注入；生产环境还应使用 TLS、合理的 QoS、断线重连和消息重发策略。

## 八、USART 与 STM32 底层实现

## 8.1 串口协议

树莓派默认通过 `/dev/ttyAMA0`、115200 波特率向 STM32 发送 ASCII 单字节命令。STM32 USART2 配置为：

```text
115200 baud、8 数据位、1 停止位、无校验、无硬件流控
```

STM32 使用中断方式逐字节接收：

```c
HAL_UART_Receive_IT(&huart2, rx_buffer, 1);
```

在 `HAL_UART_RxCpltCallback` 中解析命令，并在处理后重新开启下一次中断接收。这种方式不会让主循环阻塞等待串口。

单字节协议简单、延迟小，但没有帧头、长度、校验和、序号与确认机制。项目扩展后可升级为：

```text
帧头 + 命令类型 + 数据长度 + 载荷 + CRC16
```

并增加 ACK、超时重发和命令序号，防止干扰或丢包造成误控制。

## 8.2 ADC+DMA

摇杆的两个模拟轴接入：

- PA0 → ADC1_IN0。
- PA1 → ADC1_IN1。

STM32 启动 ADC 扫描和 DMA：

```c
HAL_ADC_Start_DMA(&hadc1, (uint32_t *)adc_values, 2);
```

ADC 连续转换两个通道，DMA 自动把结果搬运到 `adc_values[2]`。CPU 不需要轮询等待每次 ADC 转换，只需在控制循环中读取最新值，降低了阻塞和中断开销。

## 8.3 人工优先仲裁

代码设置摇杆中值和死区：

```text
JOY_CENTER = 3102
DEADZONE   = 200
```

只要任意轴偏离中值超过死区，就直接使用摇杆 ADC 值作为输出；只有摇杆处于中位死区时，才根据树莓派命令生成输出。

这是一种硬件侧优先级仲裁：即使树莓派正在发送命令，用户推动摇杆也可以在 STM32 端立即接管，不依赖 Linux 进程及时响应。

## 8.4 DAC 输出与档位

STM32 使用 PA4、PA5 两路 12 位 DAC 输出模拟控制量。根据控制码修改 X/Y 轴目标值，并调用：

```c
HAL_DAC_SetValue(..., DAC_ALIGN_12B_R, value);
```

速度分为三档，对应 0.3、0.6、1.0 的比例系数。`A` 和 `D` 只修改档位，不直接改变方向；`F/B/L/R/S` 才修改运动状态。

## 九、一次完整控制过程怎么讲

以一句语音输入为例：

1. PyAudio 每次读取 1024 帧 16 kHz 单声道 PCM。
2. 音频块送入 `KaldiRecognizer.AcceptWaveform`。
3. 程序读取 Partial 或 Final 文本。
4. 文本转换成无声调拼音音节。
5. 根据整句、句尾位置、控制提示词和近音规则选出候选命令。
6. 经过最小处理间隔、全局冷却、同指令冷却和指纹去重。
7. 检查系统是否唤醒以及当前输入模式。
8. 将命令映射成一个 ASCII 控制码并写入消息队列。
9. 串口线程从队列取出控制码，通过 `/dev/ttyAMA0` 发送。
10. STM32 USART2 中断回调接收控制码并更新状态。
11. 主循环先判断摇杆是否请求人工接管；若没有，再根据控制码计算 DAC 输出。
12. 若上层连续 60 秒无活动，软件监控线程发送 `S` 并取消唤醒状态。

以视觉输入为例，前 4 步替换为：

1. V4L2 获取最新摄像头帧。
2. 图像补边、归一化、BGR 转 RGB并转换成 NCHW blob。
3. OpenCV DNN 执行 ONNX 前向推理。
4. 解析 `[1,9,336]` 输出，完成阈值筛选、坐标转换与 NMS，选出最高分姿态。

后续仍进入同一套状态仲裁、消息队列、USART 和 STM32 控制链路。

## 十、项目中最有技术含量的三个问题

### 问题一：Vosk Partial 结果重复触发

**原因：** Partial 是累积且会反复变化的中间结果，一次讲话可能多次包含相同命令。

**解决：** 联合使用最小处理间隔、全局冷却、同指令冷却、滑动窗口指纹去重和 Recognizer Reset。

**为什么不是只做一次延时：** 固定延时会增加交互延迟，而且不能区分同一句重复结果和用户真正发出的下一条命令。多层过滤分别约束处理频率、全局触发频率和同类触发频率。

### 问题二：中文同音、近音识别错误

**原因：** Vosk 输出的是汉字文本，相同发音可能被解码为不同汉字。

**解决：** 把文本转换为无声调拼音序列，在音节层匹配；同时通过句尾和控制提示词限制触发范围。高风险近音只允许 Final 整句匹配，平衡召回率与误触发率。

### 问题三：树莓派算力有限

**解决思路：** 使用 128×128 小输入、ONNX 模型、OpenCV DNN CPU 后端、摄像头缓冲区 1、跳帧推理和单 OpenCV 线程，减少模型依赖与 CPU 竞争。

**边界：** 当前仓库没有准确的端到端延迟、CPU 占用或 FPS 测试，因此面试时不要编造指标。可以说明若继续优化，会通过 `time.perf_counter()` 分别测量采集、预处理、推理、NMS 和串口下发耗时，再决定是否进行 INT8 量化、模型剪枝或迁移到具备 NPU 的平台。

## 十一、常见面试追问与参考回答

### 1. 为什么使用离线 Vosk，而不是在线语音 API？

轮椅控制对网络依赖和隐私较敏感。Vosk 可以在树莓派本地运行，没有网络时仍可识别，同时避免把持续音频上传云端。代价是小模型准确率有限，因此我在模型输出后增加了拼音和时序后处理。

### 2. Partial 与 Final 为什么都要处理？

只处理 Final 会增加响应延迟，只处理 Partial 又容易重复和误触发。我让明确指令可以通过 Partial 快速响应，而高风险近音补偿必须等待 Final，从延迟和可靠性之间做平衡。

### 3. pypinyin 匹配会不会扩大误触发？

会，所以不能只做拼音相等判断。我还要求命令是完整句或位于句尾；短命令在长句中还需要控制提示词；高风险近音只允许 Final 整句匹配。

### 4. OpenCV DNN 和 ONNX Runtime 有什么区别？

ONNX 是模型格式，OpenCV DNN 和 ONNX Runtime 都是推理引擎。项目使用 OpenCV DNN，因为已经依赖 OpenCV 采集和处理图像，可以减少额外运行库；如果追求更高性能，应在同一硬件上基准测试两种引擎，再选择执行提供程序和线程参数。

### 5. YOLO 输出为什么是 `[1,9,336]`？

输入尺寸是 128×128，检测头在多个尺度上产生共 336 个候选位置；每个位置输出 4 个框参数和 5 个类别分数，所以通道数为 9。后处理要先转成 `[336,9]` 才方便逐候选解析。

### 6. 为什么要 NMS？

同一目标周围会有多个重叠预测框。NMS 根据分数和 IoU 保留最可信的框，抑制重复框，防止同一帧出现多个重复姿态结果。

### 7. 为什么要把 front 设为安全偏置？

当 left/right 与 front 的分数非常接近时，说明样本处于分类边界。转向误判的风险高于保持正向，因此在差值小于 0.1 时选择 front，以业务风险约束模型决策。

### 8. 为什么树莓派不直接输出控制电压？

树莓派缺少适合该场景的实时 ADC/DAC 控制能力，而且 Linux 调度不具备确定性。STM32 更适合完成固定周期采样、串口中断和模拟量输出，也能在树莓派异常时保留本地安全策略。

### 9. 为什么使用 ADC+DMA？

DMA 可以在 ADC 连续扫描时自动搬运两个通道数据，CPU 直接读取最新数组即可，避免轮询等待或高频中断，提高控制循环的稳定性。

### 10. 系统最大的安全风险是什么？

当前安全停止主要由树莓派软件线程触发。如果 Linux 进程崩溃，软件 Watchdog 也会停止工作。更可靠的方案是在 STM32 端增加通信心跳超时、硬件看门狗、输出限幅和独立急停输入，让安全闭环不依赖上位机。

### 11. 单字节协议有什么问题？

它简单、实时，但缺少校验、确认和顺序信息。电磁干扰或串口丢字节时无法检测。后续可加入帧头、长度、CRC16、序号和 ACK，并把停止指令设置为最高优先级。

### 12. 如果多人同时说话怎么办？

当前系统没有说话人识别和波束形成，只能通过近讲麦克风、唤醒状态和命令规则降低误触发。进一步可加入唤醒词模型、VAD、麦克风阵列、说话人确认或物理使能键。

## 十三、代码层面建议先修正的四个问题

### 1. 统一模型类别顺序

按当前 `best.onnx` 元数据应设置为：

```python
CLASSES = ["front", "right", "up", "left", "down"]
```

### 2. 根据模型输出决定是否 sigmoid

当前模型的类别输出已经在 0～1 范围，应直接使用；只有确认输出为 logits 时才执行 sigmoid。

### 3. 拆分消息队列

将控制命令和健康数据分别送入独立队列，避免串口线程与 MQTT 线程竞争消费同一个队列。

### 4. 合并部署版本

完整启动脚本位于 `daima/6.27`，更新后的集成控制代码位于 `daima/7.11`。部署前应把最新版模块及其依赖统一到同一目录，并完成一次树莓派端联调，避免启动入口仍加载旧版本。

## 十四、3 分钟完整项目陈述

这个项目面向无障碍出行场景，我采用 Raspberry Pi 4B 和 STM32F407 构建边缘计算与实时控制分层架构。树莓派运行 Linux 和 Python，承担 Vosk 离线语音识别、OpenCV DNN 视觉推理以及 MQTT 云端通信；STM32 使用 C 和 HAL 库完成 USART 中断接收、ADC+DMA 双通道采样、控制仲裁和双路 DAC 输出。

语音部分通过 PyAudio 采集 16 kHz、16 bit、单声道 PCM 音频，每 1024 帧送入 Vosk `KaldiRecognizer`。我同时处理 Partial 和 Final：Partial 用于降低明确命令的响应延迟，Final 用于稳定整句和高风险近音补偿。为了处理 Vosk 常见的同音汉字问题，我使用 pypinyin 把词表预构建成无声调音节索引，运行时将识别文本转换为拼音，再结合整句匹配、句尾位置和控制提示词进行判定。时序上通过 0.45 秒全局冷却、1 秒同指令冷却、最近 30 条指纹去重和 Recognizer Reset，减少一次讲话被多次执行；播报提示音后设置短时输入屏蔽，避免扬声器声音被麦克风再次识别。

视觉部分将 YOLO 模型导出为 ONNX，使用 OpenCV DNN 在 CPU 上加载。摄像头通过 V4L2 采集，图像先补齐为方形，再利用 `blobFromImage` 完成 128×128 缩放、1/255 归一化、BGR 转 RGB 和 NCHW 排列。网络输出为 `[1,9,336]`，我将它转成 336 个候选框，每个候选包含 4 个坐标和 5 个类别分数，然后执行阈值筛选、中心点坐标转换、NMS 和最高置信度选择。对于左右与正向分数接近的边界样本，我加入 front 安全偏置；时序上加入姿态变化判断和 0.4 秒防抖，控制重复下发频率。

语音、视觉和 MQTT 最终都转换为统一单字节控制码，通过消息队列交给串口线程，再以 115200、8N1 发送给 STM32。STM32 通过 USART2 中断接收命令，同时使用 ADC+DMA 连续采集摇杆两个轴。只要摇杆偏离死区，就直接采用人工输入；只有摇杆处于中位时才执行树莓派命令，保证底层人工优先。最终控制量通过 PA4、PA5 两路 DAC 输出。系统还通过独立软件监控线程检查活动时间，60 秒无输入时发送停止码并取消唤醒。

这个项目的重点不只是把几个模型接在一起，而是完成了模型部署、异构通信、并发任务调度、输入仲裁和安全控制闭环。后续我会进一步在 STM32 端增加通信心跳超时和硬件看门狗，同时完善串口 CRC 协议，并对视觉推理各阶段做性能基准测试。
